## CRITICAL RULE on recency (read this before researching anything)
Roughly 90% of what you add on any given run should be dated within the last 2-3 days (widen to ~4 days if a weekend falls in that span, per the note above). This is the default and the expectation, not an aspiration. Material older than that (but still inside whatever window the target page already allows — 14 days for This Fortnight, ~2 months for the category pages) is a narrow fallback for a genuinely major, clearly significant story that was missed in a prior run — not a tool for padding output, not a way to satisfy the Minimum coverage rule below, and not a way to satisfy the Anti-anchoring or Geographic coverage rules either (those rules mean "look for the Asia/Europe/smaller-player signal from the last 2-3 days you might be skipping," not "go find any Asia/Europe/smaller-player story from the last two months to add regardless of age"). A story from three or four weeks back does not become includable just because it's on-theme, new-to-the-site, or fills a gap in company/region coverage — age is the first filter, relevance is second. Exception: Research (arXiv/SSRN) explicitly runs on a wider 2-month fallback window by design (see its own step below) — a paper doesn't need to be from the last 2-3 days to count as a genuine, worthwhile addition, unlike news/company pages.
If, after genuinely trying hard on the last 2-3/4 days specifically (more queries, more angles, more sources — not just the first round of searches), nothing turns up for a given page, that is a completely fine and expected outcome. Add little or nothing that run rather than reaching back weeks for filler. Do not treat "I need to add something" as license to loosen the date filter. It is far better to publish an edition with two or three genuinely fresh items than one padded with ten stale ones dressed up as new.
This rule sits above the general freshness/pruning windows described below — those windows (14 days, ~2 months) define how long something is allowed to STAY on a page once added; this rule defines how old something is allowed to BE when you ADD it. Don't confuse the two.
Work through ALL categories systematically every run (Network, Emerging Rails & Stablecoins, Commerce, Market, Research, LinkedIn, Protocols, Events) rather than stopping once a couple of pages have fresh material — a category coming back empty after real effort is a fine, reportable outcome, but skipping a category's search entirely is not. Treat "one genuine search attempt per category" as the floor, same spirit as the Floors, not targets rule below. Note the Events page has its own, different recency logic — see its dedicated section below — since it's about upcoming dates, not published-date freshness.

## CRITICAL RULE on verifying how old a LinkedIn (or any dated) result actually is
Search-engine result snippets for LinkedIn posts almost never show a real date — no "3d"/"1w" marker, sometimes not even a year. Do not assume a LinkedIn post is fresh just because it surfaced for a recency-flavored query, and do not skip it just because the snippet has no visible date either. Before treating a LinkedIn result as usable, confirm how old it actually is:
- WebFetch the individual `linkedin.com/posts/...` URL and ask specifically for the relative post date (e.g. "3d", "1w", "2mo") shown near the author's name — this works for public posts without needing to log in.
- If WebFetch is blocked or unhelpful, navigate to the URL with the browser tool and read the page text/screenshot directly — public LinkedIn posts usually render enough content this way to read the relative date and the full post text (this also lets you pull the exact post text for the card description instead of guessing from a search snippet).
- Only after confirming the date falls inside the window you're working with should you use the post. A high-looking engagement count or an on-topic title is not a substitute for checking the actual date.
This same "don't trust the snippet, verify the actual date" principle applies to any other source where the search result doesn't show a clear date (press-release aggregators, syndicated wire stories, etc.) — if genuinely unclear after a real search effort, check the original/official source rather than guessing.

## CRITICAL RULE on badge-new hygiene
Every run, before publishing, verify that old badges are removed: `badge-new` should only ever be on items that are genuinely new since the *previous* run's edition — added during THIS run. If something is still carrying the badge from a prior run and isn't today's addition, clear it. This was missed for multiple runs in a row on one occasion — 26 stale badges accumulated across 6 pages, including all 12 Events entries never once cleared since the page was created — treat the check as a real, deliberate step every single run, not something you assume happened automatically as a side effect of your other edits, and not something you can skip "just this once."
**Sort order is completely independent of badge-new and must never break when a badge is cleared.** Every list on this site (Commerce, Market, Emerging Rails, Network, This Fortnight, LinkedIn, "New on Protocols") is sorted strictly by date, most-recent-first, full stop — badge-new is a visual marker layered on top, it is NOT a pinning/sort mechanism. The bug that caused the 26-badge incident above was this exact confusion: new items were being inserted at the top of a list (as if "newest = top of page") instead of into their correct chronological position relative to what's already there, so once that item's badge was later cleared it just stayed wherever it had been dropped, and the list silently drifted out of date order over several runs. Concretely, every time you add, remove, or clear the badge on ANY item in one of these lists: re-derive the correct position for every remaining item by date and fix the ordering right then, don't just prepend/append and move on. Before publishing, spot-check at least one long list (LinkedIn or This Fortnight) top-to-bottom for a date inversion (a card dated earlier appearing above one dated later) — this is the single most reliable way to catch this class of bug before it ships.
LinkedIn specifically: items with a confirmed date sort by that date, most-recent-first, exactly like every other list — but items where you couldn't confirm a real date (per the CRITICAL RULE on verifying dates above, showing an author name instead of a date) are NOT scattered wherever they happened to be inserted — they all sort to the very bottom of the page, grouped together, below every dated item. If you find a dateless entry positioned above a dated one, that's the same bug, fix it the same way.
"New on Protocols" specifically: sort by date, most-recent-first, same as everywhere else — extract the date from that row's own `<span class="org">` field only, never from its description text (a past incident: a row's `pdesc` mentioning "WAIC 2026" got misread as the row's date because a naive search scanned the whole row instead of just the org field — the fix is the same discipline as the LinkedIn date-verification rule: only trust the field that's actually meant to hold the date). "Major protocols" below it is a separate, stable curated list, not date-sorted — don't touch its order.
This applies to the Events page too (see its own section below for what counts as "new" there) — Events already sorts correctly by its own rule (soonest-first, see its dedicated bullet), the badge-hygiene failure there was purely about clearing stale badges, not about ordering.
**There is now also a code-level backstop for this**: `build.js` calls `sort-pages.js` (`sortAllPages()`) before every assembly, which re-sorts every page's cards/rows in `src/pages/*.html` by date in code — vague/dateless items always last, Events kept ascending with its two grids sorted independently, "New on Protocols" sorted only by its own `<span class="org">` date. ## CRITICAL RULE on link safety (distinct from the link-verification rule below)
Before adding any link, check it's not a security risk, not just that it resolves. If a browser/fetch tool or search result flags a URL with a malware, phishing, or security warning, drop that item entirely — don't add it, don't try to work around the warning, don't substitute another link from the same untrustworthy source. Only link to reputable, identifiable sources: established news/trade press, official company/protocol sites, arXiv/SSRN, recognized industry publications, official event/conference pages. Niche but professionally-run trade press is fine too — check for bylined authors, dated articles, editorial structure and disclaimers before trusting an unfamiliar name (e.g. stablecoininsider.org checked out this way and is fine to treat like PYMNTS or The Paypers for crypto/stablecoin-specific stories). Never use URL shorteners or link aggregators/redirectors that mask the real destination — always link the actual source (this includes `lnkd.in` short links inside LinkedIn posts themselves — if a post's own "read more" link is an `lnkd.in` redirect and you can't resolve where it actually goes, just cite the LinkedIn post itself rather than the shortened link).
NEVER save a `news.google.com/rss/articles/...` (or any Google News redirect) URL onto the site, even though the LinkedIn discovery step below uses Google News RSS to find items. That wrapper URL routes through a Google consent/cookie interstitial before reaching the real page — it's exactly the kind of opaque redirect chain that trips security warnings, and it violates this rule. When a Google News RSS result is genuinely the item you want to add, do NOT copy the RSS article link — take the extra step to find and save the real destination URL instead (for LinkedIn items specifically: the actual `linkedin.com/posts/...` URL; for other news, the publisher's own article URL, e.g. via an additional WebSearch/WebFetch or by clicking through). If you cannot confidently confirm the real destination URL for a specific item, leave that item out rather than guess or fall back to the wrapper link. Note: as of Jul 2026 there is a known backlog of pre-existing Google News redirect links left over from before this rule existed, scattered mainly across the LinkedIn page and some This Fortnight rows — resolving that backlog is out of scope for the daily run (it was spun off as its own task), don't feel obligated to fix old ones you stumble across unless it's cheap to do (you already have the real URL in hand for another reason, as happened once with a misattributed "LinkedIn" story that was actually a Salesforce blog post).
If a source is completely unfamiliar and you can't independently verify it's a legitimate outlet, either find the same story reported by a known outlet instead, or leave the item out rather than risk linking somewhere unsafe.

## Anti-anchoring rule (read before researching)
Any company/protocol name mentioned anywhere in this document (here, in page descriptions, in the search-query list below) is an ILLUSTRATIVE EXAMPLE, never an exhaustive or preferred list. Do not let these names become the ceiling of what you look for — a new, smaller, or regional player doing something genuinely relevant belongs on the site exactly as much as Visa or Coinbase does. Every run, in addition to any named-entity searches, run at least 2-3 deliberately open/generic searches with NO company name in the query (e.g. "new agentic commerce startup funding", "new AI agent payment protocol launch", "stablecoin payment rail agent launch", "new checkout AI agent PSP") specifically to surface players not already on the site. If the same 10-15 brands are the only thing that ever gets added, that's a signal the routine has become anchored — actively look for who's missing. Don't artificially cap yourself at one new item per category either: if you find several genuinely new, verified signals in the window, add all of them, not just the first one you happened to check. As with everything else, this rule is about widening WHO you look for within the last 2-3/4 days, not widening HOW FAR BACK you're willing to go — a smaller/regional player from three weeks ago is still three weeks too old by default. See the CRITICAL RULE on not anchoring on examples above — this rule and that one are two faces of the same discipline.

## Geographic coverage rule (distinct from the tag rule below)
This is a global watch, not a US-only one. English-language search results default heavily toward US/UK sources — actively counter that every run: include at least one search each for Asia (China: Alipay, WeChat Pay, UnionPay, Ant Group; also India: NPCI/UPI; Japan, Korea, Southeast Asia) and Europe (Adyen, Worldline, ECB/EU regulation, UK/EU banks, and don't overlook smaller/non-UK European markets — Switzerland, Nordics, DACH, Benelux) alongside the US-centric searches, not just when something happens to surface on its own. If a run's additions are exclusively US/UK companies several days running, that's a sign this rule is being skipped — go looking for the Asia/Europe signal you missed rather than assuming there wasn't one. Same caveat as Anti-anchoring above: this is about casting a wider geographic net over the last 2-3/4 days, not an excuse to import an older Asia/Europe story just to balance the region count.

## CRITICAL RULE on links
Before adding ANY new URL, verify it resolves (curl -s -o /dev/null -w "%{http_code}" -L -A "Mozilla/5.0" "<url>", or WebFetch). A 403 from a known corporate/publisher domain (Mastercard, SSRN, IMF, The Block, Perplexity, FIDO Alliance, e27, ai4.io, etc.) is normal bot-blocking, fine to keep. A 404 or connection failure means the URL is wrong, find the correct one via WebSearch or drop the item. Never construct a plausible-looking URL slug from memory, only use a URL you got directly from a search result or official page. Links can also go stale or get mis-attributed over time even after being correct once (e.g. a card pointing to a generic story instead of the specific one, or to the wrong date's article) — roughly every ~10 days (piggyback on the Archive cadence below), spend a pass re-checking a sample of EXISTING links across the `src/pages/*.html` files, not just newly added ones, and fix anything mismatched. See the CRITICAL RULE on link safety above for the security side of this check.

## CRITICAL RULE on numbers
Only add a numeric "Key figure" or market stat if the source states it with a precise, checkable definition (specific metric, timeframe/geography, one named source you can quote, linked via `<a class="stat">`). Skip generic "market size" or "% of commerce by year X" figures from templated aggregators. Prefer fewer, well-defined numbers over many vague ones. See the Minimum coverage rule above — Key figures are rare by nature, but that's not license to stop checking; notice a good number when you happen across one even on a run where you weren't specifically hunting for stats.

## CRITICAL RULE on dates
Prefer a precise date over a vague one. If an entry only has a bare year ("2026"), actively try to find a more precise date via search before accepting the vague one (past example: two entries sat with bare "2026" for a while until a proper search turned up exact dates). Only fall back to a vague/undated placement (sorted to the bottom) if a genuine search effort turns up nothing more specific — don't guess a date that isn't stated by a source. Note this rule is about PRECISION of a date you're already citing (exact day vs. bare year), not about how OLD a date is allowed to be when first adding a new item — see the CRITICAL RULE on recency above for that (this precision rule applies to Events too — always cite an event's actual date range, never a vague "2026").

## CRITICAL RULE on tags/labels
No "China" tag/category anywhere on the site. Chinese and other Asian players (Alipay, WeChat Pay, UnionPay, etc.) get covered by real news, tagged by what they actually are (Network/Crypto/Commerce), never a geography-based tag. Same for Timeline and Fortnight's "By major player" framing if reintroduced: list the actor, not a geography/bloc. (This rule is about how to TAG Asian players once found — see the Geographic coverage rule above for actively finding them in the first place, the two are not the same rule.)
